## Conceptual domain model

The tenant is one canonical student account (`users.id`), not an invented university/organization workspace. A student owns a profile history, consent history, saved catalog references, credit wallet, tasks, files, documents, applications and support records. Exactly STUDENT and ADMIN are formal roles (PRD BR-004/§15). Support/moderation/security/finance scopes are revocable capabilities within Admin; AI/worker/extension are controlled system actors. Admin does not own student content.

## Required enforcement specification

DBML covers PKs, ordinary unique indexes and FKs. PostgreSQL CHECKs, partial indexes, transition triggers, deferred consistency triggers, privileges and row-level security below are also required. **Exporting the DBML alone does not meet the gate.** SQL generation is a structural validation aid only; implement/verify the complete design in separately authorized phases.

### R01 — tenant keys and foreign keys

Every tenant table has non-null `owner_id → users.id`. Every reference to another tenant row includes that same `owner_id`, targeting a PK/UNIQUE tuple. For example `(owner_id, file_asset_id) → file_assets(owner_id,id)` prevents attaching another student's file even if its UUID is known. Ownership is immutable, including after deletion. No generic polymorphic private-resource FK is permitted. Audit/outbox opaque resource references carry no read authority and must be resolved by an allowlisted typed handler under the same owner.

FKs to `users.id` that denote an actor/assignee are identity references, never ownership grants. Global catalog/config references deliberately omit owner; a student can refer to a published version without acquiring moderation access. Tenant ↔ public joins never expose another tenant. Support shares preserve the original owner; assigning a ticket does not transfer ownership.

### R02 — database read isolation

Enable and **FORCE ROW LEVEL SECURITY** on every tenant and identity-private table, with both USING and WITH CHECK. Default deny; application/worker/support roles are neither table owners, superusers nor BYPASSRLS. Migration and retention roles are separate and unavailable to request/worker processes. Public access uses a security-barrier published-catalog projection with explicit columns. Operational views expose aggregate/redacted metadata, never profile facts, document bodies, filenames, storage keys or AI content.

`current_student_id()` must derive from a validated, transaction-bound session proof through a protected authorization routine. An arbitrary connection setting, client owner ID or freely settable PostgreSQL GUC is **not** an authenticated context. Revalidate session/account lifecycle and reset context on pool checkout/return; missing/stale context denies. Only server identity middleware may establish proof, not request JSON. Backend credentials remain trusted infrastructure; DB-superuser compromise is outside product-role authorization and requires separate infrastructure controls.

Workers have lease-bound capabilities for a typed job and declared immutable inputs/results. They cannot adopt an arbitrary owner's identity or scan a private library. Claim/heartbeat/finalize routines verify job ID, operation ID, owner and current fencing token. Staff have no base-table private-content SELECT. The separate moderator-report case projection in R08 permits only scoped, audited review of submitted report evidence, never profile/file-library reads. Audited support projection/download routines return only the explicitly attached object for a currently assigned ticket. Metadata-only reconciliation routines cannot return private content. Any SECURITY DEFINER routine uses fixed safe search_path, qualified objects, no dynamic user SQL and narrowly granted EXECUTE; no generic impersonation/read routine.

Owner-scoped API lookups and command authorization remain mandatory in addition to RLS. Other-user lookup → 404 + deny audit; admin library attempt → 403 + audit per A/B02. An unscoped ORM query must still fail under database policy. No direct browser/extension/Next.js database credentials, public storage ACL or shared authenticated cache.

### R03 — roles and support exception

Partial UNIQUE `(principal_id,scope) WHERE revoked_at IS NULL` on `role_grants`. CHECK `users.formal_role IN (STUDENT,ADMIN)`; normal signup fixes STUDENT, only protected provisioning can assign ADMIN. Scope grants require authorized human provisioning/evidence within ADMIN, not an additional formal Support/Finance role or mutable `is_admin` bypass. Separate scopes cover moderation, support assignment, policy administration, processor approval and credit correction. Product admin cannot grant themselves library access or manufacture legal approval. Every protected Admin command requires an unrevoked, unexpired session with verified MFA under the current auth policy; nullable `mfa_verified_at`/`mfa_factor_id` are a paired CHECK and the factor FK preserves owner; revoked/unknown factors fail; unenrolled/unverified Admin is denied. `auth_factors` stores only protected authenticator references, never raw TOTP/WebAuthn secrets in logs/settings; method/storage selection remains implementation/security review. `auth_sessions` is a protected projection to be mapped to Django session storage, not a prescribed duplicate cookie protocol. An Admin scope cannot silently confer a Student role; dual-account/merge policy remains unresolved.

See R19 for the only ticket-attachment exception. A file UUID, a ticket UUID, a past assignment or a student's upload consent alone is insufficient.

### R04 — deletion and nullable references

Every ERD FK is RESTRICT on delete/update. Do not cascade away accounting, application history or evidence. Normal DELETE is denied for journals, versions, events, results and finalizations. Approved lawful erasure is a separate least-privilege workflow (R21), not ordinary soft-delete permission. No uniqueness rule on an irreversible action includes `deleted_at`; hiding a row cannot permit another grant/debit/submission result.

For optional tuple references, CHECK that their nullable components are either all absent or all present: scholarship ID/version, document ID/version, etc. PostgreSQL MATCH SIMPLE is intentional when fixed owner/operation columns are non-null and the optional payload pair is absent. A partially-null reference must not bypass an FK. Required type-specific payloads add NOT NULL-by-kind checks (R07/R14/R15). Do not apply MATCH FULL to an entire tuple containing a fixed owner and optional version; it would reject valid empty heads.

Add a B-tree index for **each child FK tuple** unless a PK/UNIQUE/existing index already has that tuple as its leading columns; PostgreSQL does not create these automatically. Do not duplicate covered indexes. Key query indexes beyond DBML:

### R06 — activation, verification and once-only grant

Verification token digests are unique, never raw OTP/token values; consume by conditional write while locking the challenge and user. Require expiry strictly in the future, matching purpose and unconsumed state. RESTORE purpose requires same-owner deletion_request_id FK and exact pending request; all other purposes forbid that reference. An old unused restore token cannot reactivate a later deletion cycle. Activation requires verified email, explicit DOB, age >=18 and approved age policy. Record evaluated local date/time and policy; MFA and formal-role checks are independent of student age activation; Asia/Hebron evaluation is the B02 proposal. Leap-day/legal age edge rule is **MISSING**: deny unresolved activation rather than fabricate identity verification.

Activation transaction locks canonical user then wallet, validates policy, inserts the uniquely indexed SIGNUP_GRANT and updates posted balance/audit atomically. Default amount 30 is D §ب/OQ-002, configurable before admission, not a hard-coded entitlement. Grant entry amount/policy must equal the captured active signup policy; a caller cannot choose a different grant amount. Grant row remains even for configured zero; it marks the entitlement consumed. Duplicate signup/verification/OAuth-link events use the same canonical account and return its existing entitlement. Linking Google never creates a grant. No new grant on restore or policy change. A user cannot delete the grant marker.

Deleting/re-registering and merging existing accounts require an approved canonical-identity/tombstone policy (**MISSING / EXTERNAL_GATE**). Until resolved, retain minimal legally permitted anti-regrant binding or deny ambiguous re-registration/link/merge; do not promise lifetime dedupe after legally erasing every identifier. No financial journal migration/merge is inferred here.

### R07 — immutable snapshots and typed content

Updates/deletes to immutable snapshot payloads are blocked by database trigger/privilege, except approved erasure. Mutable heads use `row_version` compare-and-swap. A profile edit appends `(owner,version+1)` under head lock; a stale writer is rejected, never last-write-wins. D OQ-011 facts include nationality/residency, academic stage/qualification/field, GPA + known scale, languages and preferred countries; absent facts are Unknown, never zero/false. Exact conditional obligatory academic fields remain TBD under PRD FR-009/OQ-011. Versioned JSON validators reject unknown security-sensitive fields and unsupported GPA conversion. `profile_fact_evidence` must cover every stored fact key with origin/confirmation state and same-owner source links; drafts may use only confirmed facts. Extraction output remains a proposal until a student explicitly creates a reviewed version. EXTRACTED evidence requires a same-owner CV-extraction operation/result and a source asset from that frozen input manifest; arbitrary operation/file IDs cannot certify a fact. MANUAL evidence cannot claim AI provenance. Identity/contact/name/institution are included per PRD FR-008; exact mandatory fields still follow OQ-011.

An operation captures `profile_version`, optional paired scholarship ID/`scholarship_version`, `consent_version`, typed price row + canonical `price_snapshot`, `operation_id`, service kind, classified input manifest, explicit price authorization evidence/time, independent output language and captured local budget days **before enqueue**. These cannot change on retry. Generated-personal-document, extraction, personalized matching and account-context support require owned profile and consent snapshots. Public/synthetic operations may omit profile/consent only under an explicit service policy; no private input is then allowed. Scholarship-dependent tasks require scholarship version; CV-only tasks explicitly use no scholarship. `price_snapshot` must equal the server's canonical serialization of the referenced immutable price/policy, including credits, service kind and policy version. A trigger verifies it; client prices are ignored/rejected. `price_authorized_at`/evidence must bind the authenticated student to the displayed exact quote/request hash before reservation; a server quote alone is not student confirmation (FR-038/072, BR-029). Document/extraction language fields are validated by service kind; no worker substitutes the interface locale. Zero is legal only for explicitly free AI support/public services; unknown quote denies admission. `service_prices` CHECK requires `(chargeable AND credits>0) OR (NOT chargeable AND credits=0)`. Sourced Beta price defaults (D §ب): matching explanation 1, CV extraction 4, each CV/Motivation Letter/Personal Statement/Essay generation 6, free AI support 0; deterministic eligibility/browsing/manual editing/re-export/extension do not create a funded AI operation. Missing permitted route still denies even for zero price.

`operation_inputs` freezes owned ACCEPTED assets and purposes. AI support requires `operations.ticket_id`; an attachment input additionally binds the same operation/ticket and exact explicit share/asset through composite FKs. Required-by-kind checks reject omitted support share context; current revoked shares are not usable. Generic document/extraction inputs have no ticket context. Exact object identity/hash cannot later change. AI jobs reference one immutable operation tuple; scan/purge/notification jobs use their own typed resource version and are explicitly **not AI tasks** (no price/profile snapshot applicable). Do not copy private bodies into queue metadata. Current profile changes do not mutate a running task; a new task is required for new facts. Current consent, account state, approvals, feature flags and revocations are rechecked despite captured versions (R12/R14).

### R08 — publication, source versions and moderation

Scholarship facts, criteria and provenance are sealed as one version before review; a version is not publishable while incomplete. All current required source permissions must cover ingestion/publication, be unexpired/unrevoked, and match each provenance source via composite FK. Publishing requires scoped human APPROVED event for the exact version/hash, deterministic fact validation and expected scholarship row version. Pointer change + approval/audit/outbox commit together. Only the guarded publish routine can update visibility/published head; import/AI/ordinary draft writers cannot publish. Rejection/correction creates another version; no silent change to approved facts.

Source permission revocation or materially uncertain facts disables ingestion and public reminders; set REVERIFY or SUSPENDED through audited commands. Published projection checks current visibility/permission validity in addition to head presence. Historic versions remain for task provenance but are not publicly listed just because an old version was once approved. `source_observations` retains source/check time/content hash/material differences without overwriting reviewed facts; typed platform jobs bind source/observation through the same source key; unrelated monitor observations cannot be substituted. Probable duplicates are flagged for Admin, never automatically merged. `scholarship_reports` evidence is private to the reporter and an audited moderator case projection; immutable report events record review/outcome. Any linked moderation event must concern that report's scholarship; an upheld report cannot itself publish a new version. Report states OPEN→IN_REVIEW→UPHELD/DISMISSED are proposed, with no direct deletion/publication effect.

### R09 — eligibility is deterministic

CHECK status/coverage/score ranges; coverage and score are integer basis points (0–10,000). Finalizing an evaluation requires one check for every criterion in its exact scholarship version. Deferred validator derives INELIGIBLE if any known mandatory FAIL, UNKNOWN if unresolved mandatory facts, otherwise ELIGIBLE only with a verified complete eligibility-rule basis; no known rule basis is UNKNOWN. A known mandatory fail dominates Unknown. GPA comparison only with approved known-scale normalization. Persist engine policy and evidence; never mutate evaluation/checks after sealing.

Initial score weights 30/25/20/15/10 and >=70% coverage follow D OQ-012 defaults, subject to calibration. `score_bps` is NULL below the threshold and is never an acceptance probability. AI rationale references an existing owned evaluation; acceptance checks its snapshots match the operation and cannot update deterministic outcomes. No AI role has UPDATE on eligibility data. The matching result's validated payload requires the exact criteria contributions, coverage, confidence/limitations, explanation and rules/weights version (FR-030/031); confidence is not admission probability. Numeric confidence semantics/calibration remain an external quality gate, not an invented certainty scale.

### R10 — request identity

Unique `(owner,route,target_key,client_key)` binds canonical validated request hash (including snapshots/If-Match) to one effect. Races lock/insert the same record; same hash returns the same operation after current authorization, different hash → 409. Key format/length follows B02 (16–128 allowlisted ASCII). Target/route are server canonical values. Every operation has exactly one owned request and the request's operation back-reference must agree at commit. Non-operation routes can use the same registry without that reference. A retry never refreshes snapshots, expiry, logical day or price. Operation ID is unique independently of client key and provider attempt.

Keep irreversible request bindings for as long as operation/journal tombstones are required; cache expiry cannot mint a second effect. Replays cannot return stored bearer URLs or content after revocation/deletion. File initiation/completion dedupe binds a stable asset/version; publication/configuration use `platform_idempotency_requests` with unique actor/route/target/key, the same hash/replay rule and platform audit; no student record is fabricated for an admin.

### R11 — signed journal and wallet conservation

All credit amounts are signed integer units with checked bigint bounds. CHECK wallet `posted_balance >= reserved_balance >= 0`; counters nonnegative. Journal-kind checks: SIGNUP_GRANT amount >=0 and no operation/correction; DEBIT amount <0, exactly one operation and no correction; ADJUSTMENT nonzero and approved adjustment; REVERSAL positive, approved adjustment and one original negative DEBIT in the same owner; DELETION_CANCEL nonpositive, no operation/correction/reversal, and only by the approved final-purge workflow. Its amount is exactly minus the remaining posted wallet after all holds/sent operations are resolved, including a zero marker if already empty. One cancellation per owner is enforced independently of soft delete. Every entry has immutable actor kind/optional authenticated actor, nonempty reason and its stable entry/operation/adjustment identity (FR-077). A reversal cannot exceed its original debit; unique reversal target prevents a second reversal. Proposed two-human correction control (`approved_by != requested_by`) is an ASSUMPTION pending baseline approval. AI cannot request/approve/apply corrections. Beta corrections cannot stand in for a public payment top-up.

Append-only `credit_entries` is truth; wallet is an atomically maintained projection. Deferred constraint triggers on **every participating mutation**, not just wallet updates, enforce:

- `posted_balance = SUM(credit_entries.amount)` for the owner.
- `reserved_balance = SUM(hold.amount for operations in RESERVED/RUNNING/RECONCILING)`.
- Exactly one reservation per operation, amount = immutable price; no operation/hold without matching owner and daily reservation.
- Adjustment APPLIED iff its one matching entry exists; reversal requires authorization and original debit bound.

Active-account Credits have no time-based expiry (FR-078/AC-025). Deletion-pending/PURGING wallets are frozen by lifecycle authorization: no new reservations, grants or ordinary spending/adjustment; existing operations may only reconcile/release under evidence. Initialization produces an empty zero wallet; no API updates balances directly. Reserve checks available `posted - reserved >= price` under lock; settlement decreases posted and reserved by price; release decreases reserved only. **Releasing a hold never appends a positive refund** because nothing was debited. Post-settlement correction is a separately authorized bounded compensating entry; SETTLED never transitions back. Internal trigger writes use restricted routines, not a generally privileged mutable ledger role.

### R12 — consent, processor and dispatch safety

An AI call references immutable processor/model/region/purpose/data-class approval evidence. Admission and dispatch require current unrevoked valid approval, current consent bundle covering those exact types/purposes/region, correct classified manifest, free-only account, feature flags, dependency health and quotas. Mixed profile/public input is STUDENT_PRIVATE. Private routes only individually approved Cloudflare/Groq; Gemini unpaid/OpenRouter free private egress is categorically denied. PROHIBITED never dispatches. No seeded approval or key presence substitutes for external evidence. All provider/model names come from approval records, never client overrides.

Dispatch authorization is serialized with consent/lifecycle changes: lock user/consent head and approval, compare the captured version to current, then commit `DISPATCH_INTENT` + fenced call + physical allocations. That commit is the **linearization point for an in-flight send**. Network I/O occurs after locks are released. Revocation before that commit prevents send; revocation racing after it attempts cancellation and follows provider deletion policy. A database transaction cannot atomically revoke bytes already sent, or guarantee zero egress between intent commit and socket write. Record this limitation in consent handling; do not hold a network request inside DB locks or claim recall.

Changing consent during a task never silently switches its snapshot. Revocation denies new intents and accepted-result commit; unknown sent outcomes reconcile. Dedicated ticket attachment AI consent is required in addition to explicit human sharing. Consent rejection/security/content-validation failure cannot trigger fallback. Any unresolved previous intent blocks another generation, including provider fallback.

### R13 — daily/global/provider caps

Student spend/support and logical global days use actual Asia/Hebron midnight boundaries, not a fixed UTC offset. Store the captured day and UTC event times. Daily bucket keys exclude policy version: changing a cap cannot reset usage. Policy heads change prospectively under lock; current limits govern new admissions/dispatch, accepted holds retain their captured price. Lowering a cap below prior consumption admits no further use; it does not rewrite past consumption or invalidate accounting rows.

Defaults from D §ب: 6 Credits/day spend, 5 free AI support messages/student/day, 100 logical AI operations/day globally; these are upper bounds, not promised capacity. Admission atomically increments global logical count for **every** AI operation, including zero-credit support, and support admission count when applicable. Student daily spend check uses `credits_settled + credits_reserved + price <= current cap`. Support also checks its own limit. Finalizing moves reserved to settled; proven release reduces reserved in the **original captured day**, never today's bucket. Available wallet is separate: midnight mints no credits. Consumed logical/support admission slots remain consumed on failure/release (B02 conservative assumption).

Deferred consistency triggers enforce spend counters equal holds/debits attributed to captured day and admission counters equal immutable accepted operations. Day crossing/retry never creates a fresh logical operation. Physical call on a later day still reserves its actual provider window. Global stop/flags apply again at dispatch.

`provider_budget_windows` counts metric-specific shared-account windows, model limits and reset zones independently from student days. Prevent overlapping windows for the same quota key/metric (exclusion constraint on half-open UTC ranges, or equivalent locked registry if extension unavailable). Before **each** attempt lock every relevant window in stable order and require `consumed + reserved + conservative_max <= current cap`. Each allocation is unique per call/window and nonnegative. All applicable request/token/Neuron quotas must be reserved, including fallbacks and retries. Default 8,000 Neurons guardrail is sourced, actual free account/reset/meter is EXTERNAL_GATE. Missing safe upper bound, budget window, evidence or free-only enforcement denies dispatch.

Unknown sends retain physical allowance. MEASURED usage can release only proven unused allowance; counts must match allocations with authoritative evidence. Window rollover never erases unresolved previous allocations or grants retroactive allowance. Student release does not replenish consumed provider usage. No paid API, automatic upgrade or budget override by reconciliation. Counters and allocation state transitions are guarded and audited; telemetry alone is insufficient evidence to lower them.

### R14 — settlement, result and terminal witnesses

Only guarded lifecycle/finalization routines may change billing state or insert accepted outputs/debits/finalizations. Transition allowlist is in [state-machines.md](state-machines.md). Database triggers reject out-of-order edges and immutable-column edits even if API validation is bypassed. One locked operation serializes finalizers; terminal witness PK and result UNIQUE prevent two outcomes. Deferred consistency constraints fire on operation, reservation, result, document version, journal and finalization changes:

| Operation state | Required commit-time facts |
|---|---|
| RESERVED/RUNNING/RECONCILING | Exactly one hold; no accepted result, terminal witness or debit; hold included in wallet/day reserved totals |
| SETTLED, price >0 | Exactly one accepted validated result and SETTLED witness referencing it; exactly one same-owner/same-operation DEBIT of `-price` using the operation price policy; witness references that entry; no active hold |
| SETTLED, explicit price 0 | One validated result and SETTLED witness, no debit, zero hold no longer active; global/support slots still consumed |
| RELEASED | RELEASED witness with terminal failure/no-acceptance evidence, no result or debit, no active hold |

SETTLED result must match operation kind and immutable manifest. Its required `ai_call_id` has a same-owner/same-operation composite FK; acceptance requires that exact call to be SUCCEEDED with matching input hash and current referenced processor approval. A response-less or different attempt cannot manufacture acceptance. Document services require document ID/version pair, no generic payload, and that document version's `source_operation_id` equals this operation. Matching rationale requires matching evaluation snapshots and validated payload; extraction stores a reviewed proposal, **not an automatic overwrite of profile facts**; support stores bounded validated payload. A technically accepted draft is not yet student-approved for ready/export/submission; `document_approvals` requires `approved_by=owner_id`, an explicit student action and matching immutable version hash. Private output lives in owner-protected content tables, not `ai_calls` or audit. Validation policy/evidence is mandatory; database proofs attest validator acceptance, while semantic truth/grounding still needs implementation quality tests.

Accepted generated document version, head update, result, debit, terminal witness, job completion and audit/outbox are one transaction with current consent/account/approval and lease checks. Staged storage bytes are inaccessible until accepted pointer commits. Rollback leaves no accepted document/debit; orphan bytes remain counted until confirmed cleanup. Generation in this bounded design creates a new document; it cannot overwrite an existing document head. Regeneration into an existing document would require an explicitly captured target ID/version contract and is not enabled here. Manual head edits always use R07 CAS. Persisting staged output after any conflict requires authorized reconciliation or proved terminal failure/release. No accepted generated version may survive without the matching settled result at commit.

Expiry 15 minutes → RECONCILING, not release. 24 hours is an alert/target. Release requires evidence no accepted result exists and no uncertain pending generation can legitimately be accepted; terminal provider rejection/validated-output rejection/cancellation before dispatch can qualify. Unknown outcomes stay RECONCILING. Late results for terminal operations cannot be inserted or debit again. Existing SETTLED result is replayed only with current authorization; RELEASED late bytes purge.

### R15 — leases, retries, jobs and outbox

Jobs use typed target columns: AI → operation; scan/purge → exact file asset; reminder → notification. CHECK exactly the target allowed by kind; no arbitrary private target strings. Claim under short `FOR UPDATE SKIP LOCKED`, increment monotonic lease token, persist worker/lease then commit. Heartbeat/finalize compares current token/lease and current lifecycle. Job mutation cannot manufacture an operation transition. Proposed B02 120s lease / 30s heartbeat and max three sequential attempts remain engineering defaults, not measured capacity.

One unresolved call per operation; partial unique index plus operation lock. Call admission also rejects any previous SUCCEEDED call; all previous attempts must be KNOWN_FAILED with authoritative retryable not-executed proof before another PLANNED call is inserted. PLANNED can become KNOWN_FAILED without send; persist DISPATCH_INTENT before network. Crash after intent, even before socket send, is UNKNOWN unless authoritative evidence proves otherwise. Fenced old worker cannot insert result, append debit, change counters or heartbeat. Lease loss with possible send routes to reconciliation, never automatic retry. Only proved not-executed transient failure permits bounded retry/fallback; other terminal/validation/security failures do not. Provider-side exactly-once execution is not promised by internal IDs.

Mutation + audit + outbox insert atomically. Delivery is at least once. Each consumer stores a durable unique event ID with its effect (using notification UNIQUE, job dedupe key or a consumer-specific receipt added with that handler); acknowledge only after commit. Delivered markers alone cannot prove a downstream effect. Platform jobs/outbox accept only catalog/config/aggregate types, never student resource IDs or private payloads.

### R16 — files, scans and capacity

File state transition guards bind immutable `(owner,id,object_version,sha256)` once completion is verified. UNIQUE object key and private versioned/non-overwritable storage prevent swapping accepted bytes. Actual bytes/MIME/hash/content validation and exact-version CLEAN scan are prerequisites for ACCEPTED; outage/error/pending stays unreadable. Conditional CHECKs require object identity/hash/actual byte count for scan/accepted states; uploaded accepted byte count equals declared; system-generated staged/export assets use an explicitly reserved upper bound and require actual bytes <= that bound. Purpose distinguishes these cases, never a client override. Replacing bytes always creates a new asset/scan. Generated/export artifacts also require safe validation/scan policy before file download; staging cannot skip it.

D OQ-013 defaults: PDF/DOCX/PNG/JPG, 5MB/file, 10MB/student, 750MB global. Decimal interpretation (5,000,000 etc.) follows B02 **ASSUMPTION** pending baseline. All object-producing flows reserve owner/global capacity under locks **before** granting upload or writing staged bytes. Counters include quarantine, accepted, temporary export/staging and ticket attachment copies if any; this design shares a selected immutable asset by explicit relation, so no hidden copy is assumed. Worst-case generated/export size must be bounded or generation/export is disabled.

For uploads, reserve declared bounded bytes at initiation and verify measured equality at completion; for system-generated artifacts reserve a conservative bound before writing and reconcile only proven unused bytes. `capacity_state` (RESERVED/RETAINED/RELEASED) and `capacity_bytes` record exactly the once-accounted amount. Move reserved to retained when bytes are confirmed stored; accepted content has RETAINED capacity, PURGED has RELEASED/zero. A PURGE_PENDING asset preserves its previous allocation class until cleanup, so a failed initiated upload cannot decrement the wrong counter. Failed/expired sessions keep charged capacity while an object may exist; purge receipt alone releases it once. At every step `reserved + retained` equals outstanding asset allocations (with policy-defined bounded staging), and admission checks both current caps. Distinguish stage existence/unknown upload completion conservatively; do not free quota at database soft delete. If storage cannot enforce exact immutable key/byte limits, use bounded server streaming. Re-exporting an existing approved document version does not create an AI debit. `documents.title` rename is owner-CAS metadata; optional parent variant uses an owner-composite FK and acyclic lineage. Scholarship-specific variants bind an exact reviewed scholarship version. Each document version has language and optional earlier same-document `restored_from_version`; restoring appends a new version/head without modifying any earlier payload or copying approval automatically (FR-043/044/047).

### R17 — application history and frozen content

Application create appends sequence 1 → PREPARING and head atomically. Every transition locks owner/application, checks expected row/head, appends `head+1` with prior state and evidence, and updates head/state in the same transaction. UNIQUE sequence prevents duplicates; deferred triggers require a contiguous chain, correct `from_state`, legal edge, and head equal last event. Actor/source assertions are checked, not accepted from JSON. Official-report integration is disabled until separately specified; no AI/extension may submit an application.

Versioned `scholarship_requirements` enumerate approved DOCUMENT/FORM/ACTION requirements with explicit uncertainty. `application_checklist_items` bind the same scholarship/version as the current pinned application event; rebase to newly approved requirements is an explicit append-only history action, not silent replacement. Missing/unknown items cannot count complete. DOCUMENT completion requires the selected artifact; FORM/ACTION completion is explicit student confirmation, never inferred external submission. Preparing/Ready manifests reference either an owned, student-approved immutable document version **or** one exact ACCEPTED upload asset, using an exclusive-one CHECK and composite ownership FKs. Slot keys reference the owned checklist item. No nullable pair can evade this type rule. On student-reported SUBMITTED, copy the exact draft manifest plus hashes into `application_event_documents`, pin scholarship/profile versions and `submitted_sequence`; copy artifact hash and exclusive document-version/file binding; freeze manifest mutation. Later edits append new document versions without changing the submitted event's references. Restore never rewrites history or unfreezes a submission. A new round uses a new application, not resetting the old one. Owner notes are private; a notes/checklist-only edit appends a same-state activity event with `notes_snapshot` and reason, updating the head by CAS. Such a self-edge cannot change state, a submitted manifest or prior events. Readiness rules require verified known mandatory checklist completion plus student-approved selected versions; unknown checklist schema blocks Ready.

Corrections append an event with `correction_of_sequence` pointing to an earlier event in the same application, nonempty reason/evidence and current source attribution. They do not update/delete history or bypass normal legal status edges. Evidence-only correction may use a self-edge; reversal of a terminal/erroneous state outside the normal graph is **MISSING policy** and denied pending explicit product decision. Submitted manifest corrections preserve the original and append a new evidenced manifest; they never replace old rows. Thus some corrections remain blocked rather than silently inventing rollback rules. Lawful erasure can remove content under R21 while preserving legally allowed minimal tombstones, not mutable history.

### R18 — confirmed deadline versions and once-only reminders

Only approved current scholarship facts can produce confirmed deadline versions. CONFIRMED requires source IANA zone, unambiguous source text/evidence and verified UTC instant; unknown/date-only/ambiguous DST time cannot schedule. Version content is immutable; a new date/cancellation appends a version and moves the head. Old versions become superseded by head comparison, not rewriting their status.

D OQ-017 reminder offsets: 14/7/3 days and 24h. Proposed encoding is elapsed minutes 20,160/10,080/4,320/1,440; calendar-day versus elapsed-day DST interpretation is an **ASSUMPTION requiring product review**. Do not shift a confirmed donor instant to student timezone before subtraction. Display is local, storage is UTC. No retroactive missed reminders by default (proposed), no guarantee the student sees a delivered notification.

Unique `(owner,event_id,event_version,offset_minutes)` prevents duplicate recipient reminders across retries. Guards require eligible current saved/application relationship, verified active adult, confirmed current event and published scholarship at schedule **and delivery**. Head change/revocation/archive/deletion cancels undelivered old reminders; read history remains. Scheduling, owned job and outbox commit once. Delivery atomically sets DELIVERED + one `in_app_notifications` row linked to this scheduler record; no external email/push guarantee is introduced. The generic inbox handles source/checklist/document/credit/support events with unique `(owner,event_id,event_version,category)`, server-selected **exactly one typed destination** and composite private FKs; no client deep link bypass. `read_at` exists on the inbox, not a duplicate scheduler read state. Preferences apply only to optional categories; mandatory account/security events cannot be suppressed. Missing/inaccessible destinations remain unavailable without bypassing authorization (FR-089–093/ERR-020).

### R19 — tickets, attachment shares and SLA

A student alone can create a `ticket_attachments` share: CHECK `attached_by=owner_id`, same-owner ticket/file composite FKs, exact ACCEPTED undeleted object, explicit action/evidence. Active-share uniqueness is partial; explicit re-sharing creates a fresh row while revoked rows remain immutable evidence. Staff cannot insert a share. A read checks active support scope, current single assignment, live share, active owner lifecycle, accepted unpurged object and ticket access, then writes metadata audit before issuing short capability/stream. Revocation/unassignment blocks new reads; short-lived previously issued URLs retain the B02 bearer-expiry limitation. No support/admin traversal to sibling assets or library list. Ticket sharing does not authorize AI. Reference lifetime is under legal review; removing a library view cannot accidentally preserve a hidden unaudited share.

CHECK six canonical states: NEW, AI_HANDLING, AWAITING_ADMIN, AWAITING_STUDENT, RESOLVED, CLOSED (FR-099/BR-040); support staff are scoped Admin users, not a new formal role. Explicit CLASSIFICATION_CHANGE may append a same-state event with before/after audit metadata under the assigned-Admin command, and cannot silently rebase an existing SLA cycle; a replay does not append again. Category and priority are retained; AI suggestions never override an Admin decision. Ticket messages/events are append-only; CHECK actor/author kind against STUDENT/ADMIN/AI-or-SYSTEM as appropriate, with non-null authenticated user only for human actions and null user plus scoped operation/job evidence for AI/system actions. Do not invent an AI/support user role to satisfy an FK. Source-ingested scholarship versions likewise use explicit SYSTEM provenance rather than a fake Admin creator. Author student must equal owner, human support must be assigned and scoped at insert, AI must reference an owned support operation result for that same ticket; the operation has a same-owner ticket FK. Result/service-kind/ticket equality is checked at message insert. State changes use expected head sequence and [transition matrix](state-machines.md). Proposed one active assignee simplifies least privilege; broader team access needs an explicit policy change.

SLA cycle starts at human request/escalation, captures priority and immutable Asia/Hebron business calendar (Sun–Thu 09:00–17:00 plus versioned holidays) and target minutes: critical 240, high 480, normal 1,440, low 2,880 (D OQ-008). First substantial assigned human message, never AI/auto-ack, fills the stop marker once. FK to message plus guard verifies author kind/substantive/time. Business-time integration excludes outside hours/holidays automatically; no state/AI pause or waiting-student workaround changes first-response clock. `ticket_sla_events` records deduplicated WARNING/BREACH/ESCALATION at policy-defined business-minute thresholds; thresholds and routing not specified in available sources remain gated, not invented. Warning/escalation never falsely closes a cycle. Priority/calendar changes do not silently rewrite a captured cycle; any approved rebase must append an evidenced cycle.

D OQ-010: resolve → close after 7 days without objection; reopen within 14 days of close; one rating editable for 7 days. Proposed exact edges use UTC elapsed days, reopen `< closed_at+14d`, rating edit `< first_rated_at+7d` (boundary interpretation ASSUMPTION). Reopen starts a new SLA cycle only when human help is requested (ASSUMPTION). Rating scale is **MISSING**; feature stays disabled until defined, no invented 1–5 CHECK. AI support escalation on student request/two failures/uncertainty/financial-security issue/critical verified approaching deadline does not authorize a financial action.

### R20 — settings, audit and immutable evidence

Policy creation requires an authenticated scoped Admin with `created_by_kind=ADMIN` and a non-null creator; system-import provenance cannot grant policy-write permission. RETENTION legal_envelope_ref must resolve through guarded policy validation to a live independently approved LEGAL_RETENTION_ENVELOPE record; ordinary retention editors cannot create/waive that approval. Policy kinds have strict schemas and type-specific references (e.g. price vs SLA vs retention); a trigger validates every policy FK's expected kind and value ranges. Admin head change is CAS + audit/outbox, no retroactive edit. Source/processor approvers require distinct authorized scope/evidence; enabled flag alone cannot bypass them. Payments remain disabled; no payment/order/currency schema is speculated. Secret values never enter policy JSON; reference deployment secret names only where necessary.

Append-only tenant audit is owner-scoped with separate authorized metadata audit access; platform audit covers configuration/catalog and denial events. No prompt, file/document/message body, email/DOB, raw request, bearer URL, password/OTP/API key. Opaque resource IDs confer no traversal rights. `change_metadata` has an action-specific allowlist for relevant before/after policy/version references, operational states or Credit amounts (PRD FR-109/AC-035); it is required for sensitive changes and rejects profile/document/message bodies, filenames, emails and raw request objects. Version references resolve to immutable controlled evidence, never permission to browse another tenant. Mutating commands roll back if audit cannot commit; denied sensitive reads fail closed if their audit cannot persist. Deny audit is written in its own transaction after business rollback. Audit UPDATE/DELETE is denied to staff/app/worker; approved retention is the sole narrow exception.

### R21 — soft delete, restore, retention and purge

D OQ-005/006/020/023 are qualified operational defaults, **not legal signoff**. All instants UTC (`timestamptz`), DOB/local day `date`, IANA zones explicit. Soft deletion is lifecycle state + timestamp, never ordinary row deletion. Delete request immediately revokes sessions/new protected work/capabilities and blocks acceptance. Serialize restore/purge on the canonical user/request; capture `prior_user_state` to restore PENDING versus ACTIVE correctly. Restore uses trusted `request_at < restore_until` (exclusive boundary proposed by D OQ-020), never a client-computed date. **C03-02 resolved for design by UD-001:** Admin configures a versioned positive `recovery_days`; proposed initial 30 calendar days/Asia-Hebron uses PRD wording, not an immutable 720-hour rule. At confirmation freeze `policy_id`, `recovery_days`, `recovery_timezone`, `cutoff_algorithm=CALENDAR_DAYS_LOCAL` and computed UTC `restore_until`. Validate same-local-time calendar addition/DST resolution under ADR0008 and independently approved legal envelope; no zero/negative value or missing envelope may activate real-user retention. Later Admin edits affect new requests only, never existing cutoff/snapshot. No unconditional 2,592,000-second CHECK remains. These algorithm/zone defaults are engineering interpretation, not an invented explicit owner selection. While pending, user `deleted_at` equals the confirmed request instant, not purge completion. Restore allowed only while PENDING and before any final purge claim. An authenticated restore received before cutoff but processed later requires a durable trusted receipt and the same lock arbitration; never trust a client timestamp.

| Data class | Proposed lifecycle / retention | Trace / release gate |
|---|---|---|
| Account, profile, consent, saved items, documents, applications, tickets | Stored Admin-policy recovery cutoff, initial configurable 30 calendar days; UD-001/ADR0008; hide/deny immediately; restore same versions, journal and frozen submissions | D OQ-006/020; legal scope/which data can restore still EXTERNAL_GATE |
| Active private file bytes | After approved cutoff, target confirmed deletion within 72h; references must not silently defeat lawful erasure | D OQ-006; provider deletion capability/legal exceptions unresolved |
| Temporary uploads/quarantine/staged/export orphans | Target 24h purge; unreadable while unaccepted; capacity released only on confirmed exact-object cleanup | D OQ-006/013; B02 |

| Content-free security telemetry | Default 90 days, no student content; policy version + verified purge | D OQ-023; legal review |
| Credit journal/anti-regrant and request tombstones, financial-like audit, consent proof, support shares/messages | **MISSING approved duration/erasure basis**; do not assume security-log TTL; block real-user release until specified | A; ADR 0007; D OQ-005/006/007 |
| Catalog versions/provenance | Archive, keep referenced historical facts subject to source license; retention/revocation policy must respect permitted use | D §أ 2/3, OQ-003; source-specific legal gate |

Individual saved item/document/file soft delete hides it immediately; frozen submission references are never editable or implicitly thawed. Content purge follows approved retention/use references; a hold needs lawful documented basis, not arbitrary staff preference. When lawful deletion requires destroying frozen content, the dedicated purge role erases private bodies/keys and leaves only policy-permitted tombstone/hash/reference, or deletes dependent records in an approved ordered erasure plan. Immutability does not override erasure rights. Hashes/IDs may remain personal data; do not call them automatically anonymous.

Purge workflow marks PURGING under lifecycle lock, cancels unstarted jobs/shares, reconciles sent operations without arbitrary refunds, erases exact objects/content, records minimized receipts, confirms storage-counter decrement once, then appends exactly one DELETION_CANCEL journal event for remaining wallet Credits and records PURGED/DELETED. All holds must first have a proved terminal accounting outcome; an unknown operation blocks completion rather than being silently forgiven/debited. Legal erasure deadlines and unresolved usage/records require an approved reconciliation policy; no indefinite retention is assumed. DELETED requires zero wallet/reserved balance and the unique cancellation marker, including zero if appropriate. Restoration before the cutoff unfreezes the same balance, never cancellation or a new grant. Never let RESTRICT FKs become an excuse to retain data forever or disable constraints ad hoc; erasure migrates/redacts content under the narrow approved policy. Restored backups must replay deletion/consent revocation manifests before access. No account merge, audit TTL or retention exception is silently invented.

### R22 — transactions, lock order and deployment of constraints

Use row locks + CAS under PostgreSQL READ COMMITTED for proposed workflows; constraints are the final defense. Fixed order extends B02: canonical target user/lifecycle rows (sorted IDs) → applicable consent/policy/approval heads (sorted IDs) → budget buckets (student/global/provider/storage, stable tuple order) → operations (sorted IDs) → wallets/holds → jobs/calls/results and aggregate heads. Insert missing buckets with unique-conflict handling, then lock/re-evaluate; never trust pre-lock balance/cap reads. Lock a global window before allocating calls across workers. Single-resource handlers can omit unused stages but cannot reverse order. Revocation commands lock their head and enqueue cancellation, without synchronously walking back through already-held operation/user locks. Deadlock/serialization retries reuse the same request/operation ID and reauthorize.

No network I/O under DB locks. Atomic admission: request binding + immutable tuple + hold/wallet/day/global/support counters + durable job + audit/outbox. Atomic acceptance: owned validated result/document version + one debit + terminal witness + balances/counters + fenced job completion + audit/outbox. Atomic release: evidence + terminal witness + reserved-counter decrement + audit, without grant/refund. Failure rolls back the entire set.

Cyclic request↔operation, aggregate head↔version/event, and accepted result↔terminal/journal relationships use DEFERRABLE INITIALLY DEFERRED FKs/constraint triggers so the whole consistent graph can be written in one transaction. Head initial NULL is allowed only during aggregate creation transaction; commit-time checks require valid initialized heads for active aggregates. Deferred invariants must inspect the final transaction state, handle DELETE as well as INSERT/UPDATE, and be installed on every relevant table. Public head publication, journal-kind/amount checks and forbidden transitions also have immediate guards. Partial indexes are immediate and cannot be deferred; order writes accordingly.

Concurrency proof obligations and adversarial schedules are in [migration sequencing](migration-sequencing.md). This documentation gives implementers enforceable invariant definitions; it does not establish that any trigger, RLS policy, scanner, provider agreement or runtime concurrency test already exists.
