# Identity and extension trust contracts

2026-10-15. Documented engineering baseline, no runnable endpoints. Traces PRD FR-001–014/059–068/113–120, BR-001–006/022–025/046–052, owner Beta choices, ADR 0001/0008. Exact deployment host/client IDs/credentials/scanner/provider approvals are external configuration, never invented here.

## Registration, sessions, linking and recovery

Public email signup accepts only email/password/DOB/locale, never role/owner/grant/price. Validate explicit DOB and configured age policy on every path; declared <18 or unresolved leap-day/legal edge denies activation. Password hashing and constant-time, non-enumerating credential/reset handling use supported Django primitives. Return generic acknowledgment before verification, create no privileged session/grant. One-use digest-only purpose/account-bound verification challenges have server expiry, issuance/consume rate limits, and never log raw link/OTP. Verified eligible activation/grant/wallet/audit commit atomically under canonical-user lock and partial unique grant index.

Google authorization starts with trusted server-issued state, PKCE S256 and nonce bound to pre-auth browser session; exact approved redirect URI and client ID only. Callback validates state/nonce/issuer/audience/signature/expiry and code+PKCE before accepting provider subject. It rotates session/CSRF. A verified email claim alone never links/merges accounts: existing identity requires current authenticated session plus recent reauthentication and explicit single-use linking challenge for that account. Google-only new account must separately supply DOB and pass verified adult activation; no grant before eligibility. Provider configuration absent → controlled unavailable, no fabricated OAuth tokens. Signup/account linking/re-registration ambiguity cannot farm grants; minimal lawful identity/tombstone gate remains explicit.

Session cookie/CSRF and 24h inactivity/7d absolute proposed settings follow ADR0001, rechecked at each request. Rotate on login/privilege change; revoke on logout/deletion/suspension/recovery. Password reset invalidates prior reset challenges/sessions and never resets entitlements. No session/raw token in URL logs/localStorage/cache. Students need verified active adult status for protected features; only published catalog/policy/auth entry points are public. Pooled DB context derives verified session proof, not freely set owner GUC.

Admin pre-auth session permits only MFA challenge/verification/enrollment-security flow, not protected Admin commands. MFA proof binds current challenge/principal/factor/session and expiry, with throttling/replay denial. Authenticator secrets live encrypted/protected factor storage, no generic factor SELECT or analytics. Exact available method/backend and enrollment/recovery security approval must be configured; absence denies privileged access. All support/finance/moderation/security scopes are within Admin, not extra user roles or a superuser library bypass.

Deletion requires recent ownership proof and explicit impact confirmation, captures ADR0008 Admin policy snapshot and disables normal sessions. Independent recovery challenge verifies account while standard login remains disabled. Restore token is purpose/account/exact-deletion-request-bound, single use and timed by trusted receipt `< stored restore_until`; issue only least-privilege recovery context, never arbitrary disabled-account operations. Restore/purge serialize, no cancellation/regrant within recovery. Legal erasure and backup replay remain gated; not a new auth-provider implementation.

## Extension pairing and bounded data release

The optional Chrome MV3 extension is a public client, not a student/Admin role. Allowlist exact extension IDs/origins and permitted site registry. The website's authenticated CSRF-protected pairing-approval flow issues an opaque single-use authorization code bound to owner/session/extension instance, redirect, allowed scopes and S256 challenge; proposed 60-second code lifetime. Extension background service worker exchanges code+verifier, with exact client/origin validation, for a proposed 5-minute scoped token held only in memory. No refresh token; re-pair/re-authorize after expiry. Tokens are revocable with source session/account, audience-restricted to extension APIs and recheck current lifecycle/selected resource on every request. Never pass reusable auth material to page scripts/content scripts or portal URLs.

Only cookie-free extension code exchange uses the narrow token/PKCE protocol instead of cookie CSRF; it rejects ambient cookies and requires the prior session-approved code, PKCE and exact origin. All cookie-authenticated unsafe routes still require Django CSRF. No wildcard CORS. Extension read endpoints accept the scoped extension token; ordinary web cookies alone do not unlock them. Exact deployment allowlists absent → extension disabled G-EXT.

Default capabilities are read confirmed profile fields, selected application's approved facts and review-only attempt diagnostics; no private file library listing/bytes, credit changes, provider choice or status mutation. Each data-release request declares permitted portal ID and selected application, and server checks pairing scope + ownership + current source/site terms. Sensitive values require explicit per-attempt student selection/confirmation; unknown fields remain missing. A token/session is not site consent. Content-script/background messages validate sender extension/tab/origin against allowlist, never trust arbitrary webpage messages or user IDs.

Field mapping remains local/controlled; no password/OTP/CAPTCHA collection and no Submit or remote-save guarantee. Final external submission and internal Submitted confirmation are separate student actions. Log portal/error categories and field counts only, never values/secrets. Per-site test matrix is required; unsupported permitted pages are labeled best effort with bounded retry/manual copy alternative. No third-party AI processing of form contents unless separately classified/consented/approved. These protocol choices are assumptions with later integration/security tests, not a claim of installed extension support.
